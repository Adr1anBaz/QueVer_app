El problema que atiende, su contexto web y el recorrido de PhoneGap a Apache.

José Adrián Bazaldúa Huerta

Universidad Iberoamericana

9 de noviembre de 2026

Abra con la pregunta central: cómo usar conocimientos web para crear aplicaciones móviles. Esta primera parte explica el contexto y la historia; la segunda parte abordará arquitectura, plugins y decisiones de uso.

Un problema de plataformas

01 / problema

Una misma idea móvil podía exigir equipos, lenguajes y herramientas distintos para cada sistema operativo.

El reto: llegar a más de una plataforma sin rehacer toda la interfaz.

  1. Una experiencia para cada sistema
  2. Código y herramientas diferentes
  3. Más tiempo de mantenimiento
  4. Necesidad de reutilizar

Fuente: Apache Cordova, Overview.

No afirme que una sola base elimina todo el trabajo específico. El problema es reducir duplicación en la interfaz y la lógica web; las plataformas siguen teniendo requisitos propios.

La web ya tenía una base común

02 / contexto

HTML, CSS y JavaScript eran tecnologías conocidas para construir interfaces y comportamiento en el navegador.

Una WebView lleva ese código web dentro de una aplicación para cada plataforma.

  1. HTML estructura la pantalla
  2. CSS define la presentación
  3. JavaScript responde a acciones
  4. La app se empaqueta por plataforma

Fuente: Apache Cordova, Overview.

Explique WebView como una ventana de navegador integrada, no como un navegador separado. Cordova permite que el código web se ejecute dentro de un contenedor de aplicación.

La necesidad: web + dispositivo

03 / motivación

Reutilizar código web no bastaba si la app no podía interactuar con capacidades del teléfono.

Cordova une tecnologías web con APIs del dispositivo.

  1. Sensores y estado de red
  2. Cámara y almacenamiento
  3. Interfaz web compartida
  4. Acceso mediante APIs compatibles

Fuente: Apache Cordova, Overview.

La idea no es convertir HTML en controles nativos automáticamente. Es ejecutar una app web y ofrecer enlaces a capacidades nativas cuando la aplicación las necesita.

2008: comienza PhoneGap

04 / Nitobi

PhoneGap surgió como proyecto de código abierto de Nitobi Software en 2008.

Su propuesta conectaba desarrollo web y aplicaciones móviles híbridas.

  1. Nitobi inicia PhoneGap
  2. Se publica como código abierto
  3. Se enfoca en apps híbridas
  4. Abre el camino del proyecto

Fuente primaria: Apache Cordova, “Goodbye PhoneGap” (2020).

Esta fecha procede del comunicado oficial de Apache Cordova. Presente PhoneGap como el origen histórico, no como el nombre actual del proyecto Apache.

2011: Adobe adquiere Nitobi

05 / transición

Adobe adquirió Nitobi en 2011 y, poco después, PhoneGap fue donado a la Apache Software Foundation.

La donación separó la tecnología base de una sola empresa.

  1. Adobe compra Nitobi
  2. PhoneGap continúa como marca
  3. La base se dona a Apache
  4. Empieza una nueva etapa

Fuente primaria: Apache Cordova, “Goodbye PhoneGap” (2020).

No sugiera que Adobe desapareció del día a día de inmediato. La idea clave es la transición de la tecnología hacia una fundación y un modelo de comunidad.

Callback se convierte en Cordova

06 / Apache

El proyecto entró a la incubadora de Apache en octubre de 2011 como Callback; el nombre pasó a ser Apache Cordova.

Apache aporta un gobierno abierto basado en comunidad y contribuciones.

  1. Octubre de 2011: incubación
  2. Nombre inicial: Callback
  3. Nombre del proyecto: Cordova
  4. Proyecto Apache establecido en 2012

Fuente primaria: Apache Foundation, Board history: Cordova.

Diga que Callback fue el nombre de incubación y Cordova el nombre adoptado por Apache. La cronología de la fundación registra la creación formal del proyecto Apache en octubre de 2012.

PhoneGap y Cordova no terminaron juntos

07 / diferencia clave

Adobe anunció el cierre de PhoneGap en 2020. Apache Cordova, como proyecto abierto mantenido por comunidad, continuó.

Cierre de PhoneGap no significa cierre de Apache Cordova.

  1. PhoneGap: producto y marca de Adobe
  2. 2020: Adobe anuncia su cierre
  3. Cordova: proyecto de Apache
  4. Su continuidad depende de su comunidad

Fuente primaria: Apache Cordova, “Goodbye PhoneGap” (14 ago. 2020).

Esta distinción evita el error más común de la historia del proyecto. El anuncio de 2020 afirma expresamente que Cordova seguía activo y mantenido; no use el cierre de PhoneGap como evidencia de que Cordova terminó.

Arquitectura: capas que colaboran

09 / arquitectura

→ →

La interfaz viaja como contenido web; los plugins conectan las llamadas JavaScript con código de cada plataforma.

Fuente: Apache Cordova, Overview y Plugin Development Guide.

~45 segundos. Recorra el diagrama de izquierda a derecha: la aplicación web no salta directamente a una API nativa. La WebView ejecuta la interfaz y el puente coordina la comunicación con los plugins. Esta separación explica por qué cada plugin debe tener soporte por plataforma.

La WebView ejecuta la interfaz

10 / WebView

HTML, CSS y JavaScript corren dentro de una vista web integrada en el paquete de Android o iOS.

No se convierte automáticamente en controles nativos: sigue siendo una interfaz web.

  1. Renderiza pantallas y estilos
  2. Ejecuta la lógica JavaScript
  3. Carga recursos de www/
  4. Comparte una base visual entre plataformas

Fuente: Apache Cordova, Overview.

~35 segundos. Una WebView es el entorno donde vive la parte visible web. Aclare el límite: Cordova empaqueta la interfaz para la plataforma, pero no transforma automáticamente cada elemento HTML en un control nativo.

Puente y plugins: el acceso al dispositivo

11 / integración

Un plugin expone una API JavaScript y la conecta con una implementación nativa para Android, iOS u otra plataforma.

El puente permite pedir una capacidad; el plugin define cómo atenderla en cada sistema.

  1. JavaScript invoca una API
  2. El bridge entrega el mensaje
  3. El plugin ejecuta código nativo
  4. El resultado vuelve a JavaScript

Fuente: Apache Cordova, Plugin Development Guide.

~40 segundos. Distinga dos piezas: el bridge es el canal de comunicación; el plugin es la extensión que implementa una capacidad. Un plugin puede requerir permisos, configuración y mantenimiento por plataforma; no todo plugin ofrece el mismo soporte en todos los sistemas.

Archivos que organizan un proyecto

12 / estructura

  • config.xml
    identidad, preferencias y configuración Cordova.
  • www/
    HTML, CSS, JavaScript y recursos de la app.
  • platforms/
    proyectos nativos generados; no es la fuente principal.
  • plugins/
    integraciones instaladas para capacidades del dispositivo.

También package.json declara dependencias y plataformas del proyecto.

Fuente: Apache Cordova, Project Structure y CLI Guide.

~40 segundos. Relacione cada carpeta con su responsabilidad. En particular, señale que www es el origen de la aplicación web; platforms contiene resultados generados y se debe administrar mediante el flujo de Cordova, no como lugar habitual para editar la lógica compartida.

El CLI coordina el flujo, no reemplaza la revisión

13 / flujo

crearbase web→añadirplataforma→prepararsincronizar→compilarpaquete→distribuirfirma y tienda

Es un mapa conceptual: cada plataforma conserva requisitos, permisos y firmas propios.

Fuente: Apache Cordova, CLI Guide.

~40 segundos. No ejecute ni presente resultados de comandos. Explique que el CLI organiza el proyecto: crea la base, incorpora plataformas, sincroniza la app web y delega la compilación a las herramientas nativas. Publicar agrega revisión, firma y políticas de cada tienda.

QueVer: un ejemplo declarado, no una prueba

14 / caso local

El proyecto de referencia declara com.ejemplo.quever y carga www/index.html desde su config.xml.

En su package.json declara Android 15.1.0 y cordova-sqlite-storage 7.0.0.

  1. SQLite es un plugin externo
  2. Puede atender datos locales
  3. La declaración no prueba instalación
  4. Tampoco prueba funcionamiento

Referencia local leída: ../quever/config.xml, www/ y package.json; sin ejecución.

~45 segundos. Sea preciso: se inspeccionaron archivos, no se ejecutó QueVer, Cordova ni SQLite. El ejemplo sirve para reconocer config.xml, www y una declaración de plugin. No afirme que el plugin funciona, que la base existe o que la compatibilidad está comprobada.

Usos y límites: una decisión situada

15 / evaluación

Puede encajar en flujos internos, catálogos o productos que parten de una base web y requieren capacidades concretas del dispositivo.

La reutilización no elimina la evaluación de rendimiento, seguridad, permisos y mantenimiento de plugins.

  1. Equipos con base web existente
  2. Necesidades nativas bien delimitadas
  3. Soporte real de los plugins elegidos
  4. Cambios de Android e iOS a vigilar

Fuente: Apache Cordova, Overview y Security Guide.

~45 segundos. Estos son escenarios posibles, no una promesa de que Cordova sea siempre la mejor opción. La carga de la interfaz, los permisos, la seguridad del contenido web y el mantenimiento de los plugins cambian la decisión. Evalúe esas condiciones antes de elegir.

Conclusión: una capa web con responsabilidades nativas

18 / cierre

Cordova permite empaquetar una aplicación web y conectar capacidades del dispositivo mediante una WebView, un puente y plugins.

Su valor está en la reutilización consciente; su límite está en todo lo que la plataforma y los plugins aún exigen mantener.
